{{PROJECT}}: how the building run works

A batch goes from the owner's words to the running app: the planner writes it, the coordinator hands it out, the executor builds it, the reviewer judges it, and the integrator merges it.

1. A batch's journey (main) 2. A batch's states 3. Who spawns whom 4. Machines, locks, tests

1. A batch's journey: from the owner's words to the running app (sequence)

The main flow. Arrows are hand-offs: a spec, a session spawned, a READY FOR REVIEW line, a review file, a report, a push. While a review runs, the executor doesn't wait: it builds its next batch.

sequenceDiagram
  autonumber
  actor M as Owner
  participant P as Planner
  participant GH as origin/main (GitHub)
  participant C as Coordinator
  participant E as Executor (lane)
  participant R as Reviewer (fresh)
  participant T as Tests (under the locks)
  participant I as Integrator
  participant B as Running app

  M->>P: idea, then points from the app
  P->>P: write docs/specs/id.md (What must be true)
  P->>GH: push spec + BACKLOG row + ROADMAP
  GH-->>C: new rows in BACKLOG, in order

  C->>E: spawn (lane-brief.md, batch id, worktree, effort)
  activate E
  E->>E: plan, unit test first, build, commit per task
  E->>E: cheap checks only: types, unit, API
  E->>C: READY FOR REVIEW id base=... head=...

  C->>R: spawn (reviewer-brief.md, id, base, head) at effort high
  activate R
  par review runs
    R->>R: read spec + git diff base...head (read-only)
    R->>C: verdict + .work/id/review.md
  and executor goes on
    E->>E: cut the next batch, build it up to its own READY
  end
  deactivate R

  alt GREEN or GREEN WITH NOTES
    C->>E: review file: fix the notes, no 2nd review
  else CHANGES NEEDED
    C->>E: findings (blocker or major)
    E->>E: fix test-first, answer under "Builder's answers"
    opt a fix changes what the owner sees, or a rewrite
      E->>C: READY FOR REVIEW again
      C->>R: spawn a NEW reviewer (round 2)
      R->>C: round 2 verdict on top of review.md
      C->>E: round 2 findings
    end
  end

  E->>T: gate: e2e files of the touched areas (lock, any machine)
  E->>T: performance suite (reference machine), if any
  T-->>E: green, or reds checked alone and listed
  opt a red forces a major change
    E->>C: STOP, major change (coordinator decides on a re-review)
  end
  E->>C: DONE head=... + .work/id/report.md
  deactivate E

  C->>I: merge id (only reviewed batches)
  activate I
  I->>I: integrate.py (merge --no-ff, rows, report, decision numbers)
  I->>T: checks on main: types, unit, API, touched e2e files
  T-->>I: green, or only listed reds
  I->>GH: fetch + merge, push main
  I->>B: deploy
  I->>GH: ROADMAP "What's new"
  I->>C: pushed sha + numbers
  deactivate I

  C->>M: short status
  M->>B: tries it
  B-->>M: right, or wrong
  M-->>P: new points (the loop starts again)

2. A batch's states

The same journey, seen from the batch. Minor findings never send it back to review; a major one may (the coordinator's call).

stateDiagram-v2
  direction LR
  [*] --> Planned: spec + row pushed
  Planned --> Building: coordinator assigns a lane
  Building --> ReadyForReview: types + unit green
  ReadyForReview --> InReview: fresh reviewer spawned
  InReview --> Fixing: findings
  Fixing --> InReview: major change, round 2
  Fixing --> Gate: notes fixed or answered
  InReview --> Gate: GREEN
  Gate --> Fixing: red that is ours
  Gate --> Done: report written
  Done --> Merged: integrator, checks on main
  Merged --> OnBoard: push + redeploy
  OnBoard --> Planned: the owner's new points
  OnBoard --> [*]

3. Who spawns whom

Only the coordinator spawns. At most {{EXECUTORS}} executors (lanes on a second machine count) and 1 integrator, plus a fresh reviewer per review.

flowchart TB
  M([Owner]) -->|idea, points| PL[Planner session]
  PL -->|specs + rows| GH[(main / origin)]
  M -->|"go, wrap up"| C{{Coordinator}}
  GH --> C
  C -->|"spawn, medium or high"| E1[Executor lanes
one worktree each]
  C -->|"opencode run over ssh"| RL[Lanes on machine B]
  C -->|"spawn per review, high"| RV[Reviewers
read-only]
  C -->|"spawn, medium"| IN[Integrator]
  E1 -->|READY / DONE| C
  RL -->|status.md lines| C
  RV -->|review.md + verdict| C
  IN -->|push, deploy| GH
  IN --> APP[[Running app]]
  APP --> M

4. Machines, locks and where each test runs

Each machine runs one locked e2e run at a time with all its cores; builders spread their e2e files over machines; performance budgets are measured on one reference machine.
