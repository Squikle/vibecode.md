{{PROJECT}}: how the agents work together

The owner talks to the coordinator. The planner decides what to build (with a pre-groomer per heavy task), the CTO decides how it is built, lanes build it, reviewers judge it, the integrator merges it, the librarian keeps the docs short. Sources: docs/workflow/ (coordinator, cto, librarian, pregroomer, briefs), docs/PLANNING.md, docs/HANDOVER.md.

1. Who starts whom

The owner starts two sessions: the coordinator (their entry point) and, to plan, the planner. Everything else is started by them. Helpers (a cheap read) can be used by any session.

2. A big task, from the owner's words to the app

The coordinator routes; it asks the owner once whether the CTO checks the planned rows (yes is recommended for every Tech: heavy row).

  M->>C: a feature, feedback, a reorder

  C->>T: tech gate for the heavy rows
  T-->>C: How to build in each spec, or a refactor row first
  C->>E: lanes build in order (section 4)

3. T-shaped grooming

The planner is the bar: it sees every spec, decision and the order. Each pre-groomer is a stem: it digs into one task with a fresh, small context and writes a report; the planner checks it against the wide view, steers it, and writes the spec itself.

flowchart TB
  P["Planner: all specs, decisions, order, architecture budgets"]
  P --- G1["Pre-groomer: task A
need, today, options, requirements"]
  P --- G2["Pre-groomer: task B"]
  P --- G3["Planner grooms small task C itself"]
  G1 --> R1[".work/groom/A.md"] --> S1["spec A (planner)"]
  G2 --> R2[".work/groom/B.md"] --> S2["spec B (planner)"]
  G3 --> S3["spec C"]

4. The batch loop

Review before the slow tests. A green or green-with-notes review ends in the reviewer's own fixes and gate, so the executor retires at READY FOR REVIEW; only a real major goes back to it, and a fresh reviewer then checks the delta only (docs or tools only: on the mid model). A reviewer averages ~44k context per call, an executor 86-148k. A design question goes to the CTO, a product question to the planner.

  A["spec ready
How to build if heavy"] --> B["executor builds
types + unit, docs, report"]
  B -->|"READY FOR REVIEW
(executor retires)"| R{reviewer}
  R -->|"green, or only minors and nits"| F["reviewer fixes its own notes
in the executor's worktree, runs the gate"]
  F -->|"READY TO MERGE"| I["integrator: merge, gate, push,
deploy, roadmap, size line"]
  R -->|"real blocker or major"| E2["executor fixes
(it knows the design)"]
  E2 -->|"READY FOR REVIEW"| R2{"fresh reviewer
delta only"}
  R2 --> F
  R -->|design question| T[CTO]
  T --> E2
  I --> APP[(running app)]

5. Clean stages

Every ~10 feature batches, on a 🔴 smell, or when known reds keep growing, the coordinator proposes a stage: no new features until the code and docs are clean again. The first one is heavy.

flowchart LR
  S[features paused] --> W[CTO health sweep
refactor rows 🔴🟠🟡]
  W --> O[planner orders them
the owner sees the list]
  O --> X[lanes refactor
no behaviour change]
  X --> D[librarian pass
contradictions, compaction, budgets]
  D --> Z[features again]
